## How to open the backend locally (2026-10-18)
- **Use `run-local.bat`** (repo root; double-click it or run it from a terminal; `run-local.bat 8011` for another port). It sets `DB_ENGINE=sqlite`, `SQLITE_DB_PATH` (`backend\data\local_dev.sqlite3`, gitignored), and `USE_SEED_DATA=true`, then runs `runserver` on `127.0.0.1:8000`. Paths come from where the file sits, so it works in any clone. It prints which database file it will use, and Django's own answer, before it starts, and it refuses to start unless Django resolved SQLite. If the SQLite file does not exist yet, it says so and runs `migrate` first. The frontend needs no counterpart: with no `REACT_APP_API_BASE_URL` it already talks to `http://<host>:8000/api`.
- **Opening the backend WITHOUT it can touch the LIVE database.** `backend\.env` (gitignored, per machine) can hold the live connection, and a plain `python manage.py runserver` reads it. This happened once on 2026-10-17 (a local runserver pointed at live and the no-show sweep ran). If you start the server by hand, set the three variables first, and never set `REACT_APP_API_BASE_URL` to the live site while developing.
- The script holds no password, token or secret and never reads or changes `backend\.env`. On a machine with no `backend\.env` it makes a throwaway `SECRET_KEY` and `DEBUG=true` for that run only (that path was not tested here: this machine has the file).
- **A trap found on 2026-10-19: `run-local.bat` migrates only when the SQLite file does not exist.** An old `backend\data\local_dev.sqlite3` stays at the migration it had (here 0056, while the code was at 0061), and the server starts anyway with unapplied migrations; pages that use a newer column or table then fail. After pulling new migrations, migrate the local file by hand, with SQLite forced and checked first (PowerShell, from `backend\`: set `$env:DB_ENGINE="sqlite"`, `$env:SQLITE_DB_PATH` to the file, `$env:USE_SEED_DATA="true"` and `$env:DATABASE_URL=""`; print what Django resolved; run `manage.py migrate` only if it says `sqlite3`). The same command with no variables set goes to the LIVE database.
